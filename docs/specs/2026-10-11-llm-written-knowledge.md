# LLM-written knowledge that reads well

Status: **exploring** (2026-10-11). Nothing here is agreed. This is the first investigation for [#74](https://github.com/Kieranties/kiln/issues/74). It records what the kit already gives, what the two routes actually do, and what the experiment needs before it can run.

The goal from the issue: most knowledge is written by the LLM, and it still reads well to a person in Obsidian ([vision](../vision.md) P1). The pattern is Karpathy's [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).

## The pattern, in short

The gist names three layers and three operations:

| Layer | What it is | Who owns it |
|---|---|---|
| **Raw sources** | Curated documents. "Immutable: the LLM reads from them but never modifies them" | Me |
| **Wiki** | Summaries, entity pages, concept pages, comparisons, an overview | The LLM, "entirely" |
| **Schema** | A file such as `CLAUDE.md` that says how the wiki is structured and which workflows to follow | Both of us, evolved together |

- **Ingest:** read one source, discuss the takeaways, write a summary page, update the entity and concept pages it touches ("a single source might touch 10-15 wiki pages"), update the index, append to the log. The gist prefers one source at a time with the person involved.
- **Query:** read `index.md` first, drill into pages, answer with citations. A good answer can be filed back as a page.
- **Lint:** contradictions, stale claims, orphans, concepts without a page, missing cross-references, gaps a search could fill.

The gist does not fix a page template, a citation format or a contradiction workflow. It expects the schema file to supply them. In kiln, **the kit already is that schema**: the type definitions, templates and conventions in `kit/`.

## What the plugin does

[Karpathy LLM Wiki](https://github.com/green-dalii/obsidian-llm-wiki) (`karpathywiki`, v1.28.0, Apache-2.0, very active). Read from its source on 2026-10-11. Items marked *inferred* were not confirmed by a test.

| Area | What it does |
|---|---|
| **Where it writes** | Only under its own folder (`wiki/` by default), in fixed subfolders `entities/`, `concepts/`, `sources/`, plus `index.md`, `log.md`, `contradictions/` and `schema/config.md`. Source notes are never edited |
| **Note shapes** | `type: entity`, `concept` or `source`. Its own frontmatter: `created`, `updated`, `sources`, `tags`, `aliases`, `reviewed`, `stub`, `contradictions`. Fixed sections such as Description, Related Entities, Related Concepts, Mentions in Source |
| **Links** | Full-path, slugified: `[[entities/page-name\|Display Name]]` |
| **Provenance** | `sources:` in frontmatter (append-only); a Mentions in Source section of verbatim quotes; `^[Source: [[Name]]]` footnotes on paragraphs of multi-source pages |
| **Index and log** | The index is generated by code, not the LLM: three flat lists with summary and aliases. The log is append-only, `## [YYYY-MM-DD HH:MM] ingest \| title`, with created and updated pages |
| **Lint** | Duplicates, dead links, empty pages, orphans, missing aliases, contradictions; in code also tag vocabulary, ungrounded quotes (a quote not found in its source) and source drift. Counts are shown before any paid fix runs |
| **Duplicates** | The LLM rewrites the surviving page, links are retargeted vault-wide, and the duplicate is **moved to the trash** |
| **Contradictions** | Found at ingest. A marker on the page and a record in `contradictions/`, resolved by hand. "Preserve both sides with attribution" |
| **`reviewed: true`** | On ingest the LLM is told the body is authoritative and may only add a `## New Information (<source>)` section. Enforced by the prompt: the model re-emits the whole body. *Inferred:* the lint fixes (merge duplicates, fill empty pages) do not check it, and a merge can trash a reviewed page |
| **Inputs** | Markdown, PDF and images. Office files only through MinerU, which uploads the file to mineru.net or a self-hosted MinerU |
| **Model** | 16+ providers. Its own API key, or a local model. Cannot use a Claude subscription or Claude Code session |
| **Customising** | `schema/config.md` can be edited, and its sections feed the prompts. The prompts themselves are hard-coded; there are no custom templates or folders per type |
| **Outside Obsidian** | The engine needs the Obsidian API. A separate `karpathywiki-cli` does ingest only (not inspected) |

## Findings

### 1. The plugin cannot write the kit's types

Its folders, `type` values, frontmatter keys, sections and link style are fixed in code. A plugin note breaks four kit rules at once:

- **Frontmatter only from the type definition** (`tests/kit/examples.test.ts`, "every note matches its definition"): `updated`, `sources`, `reviewed`, `stub` and `contradictions` are not kit properties.
- **Folders per type:** `wiki/entities/` is not `People/`, `Organisations/` or `Products/`.
- **Archive, never delete:** a duplicate merge trashes the absorbed page.
- **Links written into sentences:** Related Entities and Related Concepts are link lists.

So the choice in the issue is not "plugin or skills writing the same notes". The plugin writes **a second, parallel set of notes** in its own shapes. Using it means either living with two shapes for knowledge, or forking it. This narrows the real options to:

| Option | What it means |
|---|---|
| **A. Skills on the kit types** | Claude writes `person`, `organisation`, `product`, `topic` and `reference` notes; the mechanics below are built as skills and checks |
| **B. Plugin beside the kit** | The plugin owns `wiki/`; the kit owns work and time. Two shapes for "who is Priya" and "what is the Club Console" |
| **C. Fork the plugin** | Replace its shapes with the kit's definitions. Large and permanently behind upstream |

The current lean (A, borrowing mechanics) gets stronger from this. The experiment is still worth running, as a test of **reading quality** rather than of fit: does the plugin's prose read better than Claude's on the same sources?

### 2. Most of the mechanics already have a home in the kit

| Mechanic | Plugin | Already in the kit | Gap |
|---|---|---|---|
| A summary page per source | `sources/` page | **`reference`**: "a summary that links to the source, named with the source's own title". Gist and Why it matters | None for the shape. Raw local files (a PDF, a transcript) have no home yet: see finding 4 |
| Compiled notes say where they came from | `sources:` frontmatter, quotes, footnotes | Nothing on persisting types. `research` has a Sources section; `topic` has `verified` | **To decide:** see finding 3 |
| An index Claude reads first | Generated `index.md` | `summary` and `aliases` on every note, and the Bases views. Claude can read every note's frontmatter in one pass at ~900 notes | Probably none. A generated index is cheap to add later if reading frontmatter proves slow |
| A log of changes | `log.md` | The daily note's `## Log`, which Claude already writes to (flow 4) | **To decide:** whether ingest lines go in the daily log or a separate log. The flows already ask "what earns a log line from Claude" |
| Lint | Built | `tests/kit` checks the sample: frontmatter against definitions, links resolve, file names, no title heading | The checks run on the sample, not on a vault. Orphans, missing aliases, duplicates and contradictions are not checked |
| Hands off | `reviewed: true` | **`review`** exists, but means the opposite: "the reason a note needs my review" | **To decide:** see finding 5 |
| Dedup on ingest | Semantic match against existing pages | Triage already "finds related notes per item" (flow 2) | The skill must search before it creates. `aliases` is the main lever |

### 3. Provenance: three ways, one fits the readability rules best

| Way | Reads well? | Checkable? |
|---|---|---|
| **Links in the sentence** to the reference note: "Renewals retry for three days ([[2026-10-05 Retry failed renewals for three days\|decided]])" | Yes: the issue's own rule, "links written into the sentences" | Partly: a check can require a link to a `reference`, `research` or `decision` in each claim paragraph |
| A `sources` links property on persisting types | The sentence stays clean, but the claim and its source drift apart | Yes, and a Base can list them |
| Footnotes, as the plugin does | Obsidian renders them well, but they read as an academic paper | Yes |

Lean: links in the sentence, to `reference`, `research` and `decision` notes. It needs no new property, and the existing views (`topic-references`, `topic-decisions`) already show the reverse. A `sources` property can follow if the experiment shows claims that cannot carry a link.

### 4. The experiment has no raw sources to ingest

`tests/fixtures/layer1` holds **compiled** notes: 16 short notes, already in the kit's shapes. There is nothing raw to compile them from. Running either route over it would ingest notes that are already the output.

The experiment needs a set of fictional raw sources first, for example in `tests/fixtures/sources/`:

- a renewals standup transcript (meeting);
- a Slack-style thread on grace periods;
- the body of GitHub issue #88 and its comments;
- a payment provider's retry documentation, as a PDF, to test non-Markdown input;
- a short onboarding doc for Vale Rovers.

Between them they should name Priya, both organisations, the Club Console and renewal payments, contradict each other once (say, three-day retries against five), and mention one person and one product that have no note yet. Then both routes have the same input, and the existing layer 1 notes are the "expected" shape to compare against.

Where raw sources live in a real vault is the open capture question in flow 1 ("in the visible tree, or somewhere out of sight"). Vision P8 already answers it for remote systems: the source stays remote and the reference note links its `url`. Only local files need a folder.

### 5. "Hands off" needs a property, and the kit already has a near-miss

`review` holds "the reason a note needs my review" and feeds the Needs review view. A hands-off flag is a different fact: who owns the prose. Options:

| Option | Effect |
|---|---|
| A new shared property, e.g. `written: me` (empty means Claude may write) | One property, visible in the sidebar, a Base can list my notes. Added to `properties.md` and every definition |
| A per-section rule: Claude writes the type's sections, never `## Notes` | No new property. `person`, `organisation` and `topic` already end their prose with Notes, which reads naturally as mine |
| Both | The flag for whole notes I wrote; the section rule for notes we share |

Lean: the section rule first, since it costs nothing and matches the "meeting note is both" open question in flow 3. Whatever is chosen, **a skill can enforce it better than the plugin does**: write only the target sections and leave the rest of the file byte for byte (the CLAUDE.md rule "writes are targeted"), and add new information to a protected note as a `review` reason plus a proposal, not as an edit.

### 6. One item on the readable list contradicts the kit

The issue's first readable rule is "a title heading, then a summary of a sentence or two". The kit decided the opposite: **no title heading**, because Obsidian's inline title shows the file name ([layer 1 design](2026-10-11-layer-1-structure-design.md), Page layout). Two tests enforce it (`notes have no title heading` in `examples.test.ts` and `templates.test.ts`).

The kit's equivalent is the inline title, then `summary` in the properties sidebar, then the first section as "the readable lead, the long form of `summary`". Suggest restating the rule as: **"`summary` is set, and the first section opens with a readable lead."**

### 7. What a check can and cannot judge

| Rule | Structural check | Judged by me |
|---|---|---|
| `summary` set, one or two sentences | Yes: present, under ~40 words | Whether it says the right thing |
| Frontmatter only from the definition | Already checked for the sample | |
| Sections from the template, in order | Already checked for templates; not for notes | |
| Links in sentences, not lists | Yes: no list item that is only a link, outside view sections | |
| Each claim traceable | Partly: each prose paragraph in a persisting type links a reference, research or decision | Whether the link supports the claim |
| No orphans, dead links, missing aliases | Yes | |
| Duplicates, contradictions | Needs the LLM | Which side is right |

The structural rules are cheap to add to `tests/kit` for the sample, and the same code can later run over a vault as the lint pass (vision "Open": checking Claude's writes).

## Suggested next steps

Each is a separate piece of work, in this order:

1. **Restate the readable list** on #74 to match the kit (finding 6), and add the provenance and hands-off leans (findings 3 and 5) as the things the experiment tests.
2. **Write the fictional raw sources** (finding 4). Northwind Arena only.
3. **Run the Claude side** in a session: a draft ingest skill that writes the four types plus references from those sources, following the kit's definitions and the leans above.
4. **Run the plugin side** on a local trial vault. This needs Obsidian and a plugin API key, so it is the owner's step; it cannot run in a cloud session.
5. **Read both side by side** and record the decision in `docs/vision.md`.

## Open questions

From the issue, with what this investigation adds:

- **Which types does the LLM maintain on its own?** A starting split: `reference` fully Claude's; `person`, `organisation`, `product` and `topic` Claude's outside `## Notes`; `decision` and past `daily` notes never rewritten, since they are records of a moment.
- **How are writes reviewed without checking every note?** The log lines from each ingest (finding 2), the structural checks (finding 7), and `review` set only when Claude is unsure or a protected note has new information.
- **Does this change `capture`, or how sources are held?** Probably not for remote sources (P8). Local raw files need a folder, and that answers the flow 1 question about where captured sources live.
