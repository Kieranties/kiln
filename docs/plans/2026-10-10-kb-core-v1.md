# kiln KB core v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build kiln v1: a per-session MCP server, CLI and Claude Code plugin. From any Claude session it captures knowledge (including external items fetched by Claude), files it into a typed, human-readable markdown vault, and answers questions from that vault.

**Architecture:**
- A TypeScript package (`kiln`) provides a synchronous core: config, frontmatter patching, schema, placement, a SQLite index and a write store.
- The core is exposed through an MCP stdio server (`kiln mcp`) and a CLI.
- Every Claude session starts its own server. All sessions share one SQLite index per base, and writes are serialised by a `BEGIN IMMEDIATE` transaction.
- A Claude Code plugin in `plugin/` registers the server and ships the four skills (capture, triage, recall, review) and two hooks (write guard, session orientation).

**Tech Stack:**
- Node ≥ 24 and TypeScript (ESM)
- `node:sqlite` (FTS5, contentless)
- `@modelcontextprotocol/sdk` + `zod`
- `yaml` (parse only), `picomatch`, `ulid`
- `vitest`

**Spec:** `docs/specs/2026-10-10-kb-core-design.md` (lean v1)

## Global Constraints

- **Runtime:** Node ≥ 24 on Windows 11 (primary). Use `node:sqlite`; no native npm modules.
- **Registry:** a repo-level `.npmrc` with `registry=https://registry.npmjs.org/` (the user's global npm config points at a private registry).
- **Determinism:** kiln code never calls an LLM, never makes network calls, and holds no external credentials.
- **No deletes:** kiln never deletes notes. It archives through `status` and dismisses sources through `triage`.
- **No real data:** no real knowledge in the repo or tests. Fixtures are generated content about a fictional organisation.
- **Folders:** base layout exactly as spec §4:
  - `anchors/{organisation,product,service,person,topic}/`
  - `projects/`
  - `work/<year>/`
  - `decisions/<year>/`
  - `references/`, `notes/`, `attachments/`
  - `sources/{jira,github,slack,email,meeting,web,note}/`
  - `views/`
  - `.kiln/index/kiln.sqlite`
- **Field names:** frontmatter field names, types, kinds and statuses exactly as in spec §4, plus `triage_outcome` on sources (see Task 10).
- **Byte preservation:** a write changes only targeted frontmatter keys and sections. EOL style and untouched bytes are preserved.
- **Numeric parameters:**
  - re-check interval 10 000 ms
  - full-rebuild threshold 30% of files changed
  - SQLite `busy_timeout` 5 000 ms
  - file-lock retries: 5 attempts at 100 ms
- **Search weights:** bm25 weights title 5, aliases 3, summary 2, keywords 0.5, body 1.
- **Boosts:** anchor 1.6, project 1.3, work 1.3; decision active 1.6, proposed 1.3, superseded 0.4; all other notes 1.0.
- **Duplicate detection:** title similarity is word-token Jaccard. A create conflicts when:
  - `dedupe_key` is equal, or
  - it is the same type and title similarity ≥ 0.85, or
  - it is the same type with an identical `sources` set and title similarity ≥ 0.5.
- **Acceptance targets:**
  - At 100k notes: cold build < 60 s, re-check < 2 s, p95 ranked query < 300 ms.
  - Triage outcome accuracy ≥ 90%.
- **Paths:** stored base-relative with forward slashes. Base-path comparisons are case-insensitive on Windows.

## Review Focus

1. **Hand-edited frontmatter with unusual YAML** (comments, block scalars `|`, anchors `&x`, odd indentation). Patching one key must leave everything else byte-identical. Unparseable YAML must give a `validation` error and no write. *(Task 4 and Task 10 tests.)*
2. **Windows path and filename quirks.** These include:
   - backslash vs forward-slash paths and drive-letter case in hook input and config;
   - titles containing `: ? * " < > |`;
   - names that collide, which must become `Title (2).md`.

   *(Task 2, Task 7 and Task 17 tests.)*
3. **Hand-written notes with no frontmatter or no `id`.** They must be indexed by path, findable by search and `get(path)`, and updatable by path. *(Task 8 and Task 10 tests.)*
4. **CRLF files**, e.g. produced by git `autocrlf` on Windows. Patches and section edits keep CRLF. The revision is the hash of the exact bytes. *(Task 4 and Task 5 tests.)*
5. **A file held by Obsidian, Defender or sync during rename** (EPERM/EBUSY). kiln retries 5×100 ms, then raises a `locked_file` error, and leaves no temp file behind. *(Task 10 test, via an injected rename function.)*

### Task 4: Byte-preserving frontmatter patcher

**Files:**
- Create: `src/patch.ts`
- Test: `tests/unit/patch.test.ts`

**Interfaces:**
- Consumes: `splitNote`, `renderScalar` (Task 3).
- Produces: `patchFields(text: string, set: Fields, unset?: string[]): string`.

**Algorithm.** The algorithm is not determined by tests alone, so it is pinned here:

1. **Find key ranges.** Within the frontmatter, a top-level key line matches `/^([A-Za-z_][\w-]*):(.*)$/`. Its range extends over the following lines that are indented or start with `- `, and stops at the next top-level key, a comment line `#…`, or the closing `---`.
2. **Replace an existing key's range in its existing style:**
   - flow list `[...]` → flow list `[a, "b"]`;
   - block list → block list using the original item indent and dash prefix;
   - a scalar → the same quote style as the original (single, double, or plain if `renderScalar` would be plain, else double), keeping a trailing ` # comment`.
3. **New keys** are appended before the closing `---` in `renderNote` style.
4. **Unset** removes the key's range.
5. **Line endings:** use the file's EOL for all inserted lines.
6. **No frontmatter:** if the text has none, create a block at the top.

- [ ] **Step 1: Write the failing tests.** Each asserts the full output string:
  - `changes only the targeted scalar line`: a 10-key note; set `status`; `diff` shows exactly one changed line.
  - `preserves comments and blank lines elsewhere`
  - `preserves a block scalar (|) under another key`
  - `keeps flow-list style when replacing a flow list`
  - `keeps block-list indent when replacing a block list` (original indent 4 with `    - `)
  - `preserves single-quoted style for a scalar` (`title: 'x'` → `title: 'y'`)
  - `keeps a trailing inline comment`
  - `appends a new key before closing fence`
  - `unset removes the whole key range`
  - `preserves CRLF throughout` (input CRLF; output contains no lone `\n`)
  - `creates frontmatter when none exists`
  - `leaves anchors/aliases (&x / *x) under other keys untouched`
- [ ] **Step 2: Run the tests and confirm they fail.**
- [ ] **Step 3: Implement `patchFields` per the algorithm above.**
- [ ] **Step 4: Run the tests and confirm they pass.**
- [ ] **Step 5: Commit.** `feat: byte-preserving frontmatter patcher`.

### Task 9: Read API: search, resolve, matchAnchors, query, brief, get, inbox, status

**Files:**
- Create: `src/index/read.ts`
- Test: `tests/unit/read.test.ts` (a handmade 12-note base built in the test)

**Interfaces:**
- Consumes: `Index` (Task 8).
- Produces (methods on `Index`, implemented in `read.ts`):
  - `search(p: { q: string; variants?: string[]; scopeAnchors?: string[]; autoScope?: boolean; limit?: number }): SearchHit[]`
    - Defaults: `autoScope` true, `limit` 20.
    - Terms are the stemmable non-stopword words of `q` plus the variants, OR-joined.
    - Score is `bm25(fts, 5, 3, 2, 0.5, 1) × boost`, ordered in SQL over all matches.
    - With scope (explicit, or from `matchAnchors(q)` when `autoScope`), the result order is: matched anchor notes, then hits linking any scope anchor, then the remaining hits.
  - `SearchHit = { id: string|null; path: string; title: string; type: string|null; kind: string|null; status: string|null; score: number; snippet: string }`
    - The snippet is the `summary` if present, else the first body line containing a term, max 200 characters.
  - `matchAnchors(text: string): string[]`: titles of anchors and projects whose title or alias occurs in `text` at word boundaries, case-insensitive, ignoring aliases of ≤ 2 characters.
  - `resolve(name: string): { matches: NoteRef[]; brief: Brief | null }`. Tries an exact alias match first, then an FTS match restricted to anchors and projects. `brief` is for the top match.
  - `query(f: { type?: string; kind?: string; status?: string; anchors?: string[]; project?: string; review?: boolean; triage?: string; updatedAfter?: string; limit?: number }): NoteRef[]`
  - `brief(idOrPath: string): Brief`, where `Brief = { note: NoteRef; summary: string; currentTruth: string; activeDecisions: NoteRef[]; openWork: NoteRef[]; recent: NoteRef[] }`:
    - `currentTruth` is the `## Summary` section capped at 1 500 characters.
    - Decisions and work are those linking the note: decisions with status active or proposed, work with status active or blocked. Up to 10 each.
    - `recent` is the 5 most recently updated linked notes.
  - `get(idOrPath: string): NoteRecord`, where `NoteRecord = { id; path; fields: Fields; body: string; revision: string }` and the revision is the sha256 hex of the bytes. A missing note raises `KilnError('not_found')`.

  - `status(): { base: string; notes: number; inbox: number; needsReview: number }`

  - Work through `query({review: true})` plus `validate` possible duplicates.
